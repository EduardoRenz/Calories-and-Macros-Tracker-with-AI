# ADR-002: Inline Rate Limit Check in Route Handlers

## Status

Accepted

## Date

2026-07-23

## Context

The rate limiter needs an integration point within the request flow. The codebase has no Next.js Edge Middleware (`middleware.ts`), and all API routes follow a consistent pattern: extract auth header → check access via `checkAiAccess` → parse body → call service → return result. The `checkAiAccess` function already uses the `NextResponse | null` return pattern where returning a `NextResponse` short-circuits the request.

## Decision

Integrate the rate limit check as an inline call within each route handler, using the same `NextResponse | null` return pattern as `checkAiAccess`. Each route explicitly passes the endpoint category string (e.g., `'chatbot'`, `'food_analysis'`) to the check function. The rate limit check runs after auth verification but before the main service call.

## Alternatives Considered

### Alternative 1: Next.js Edge Middleware

- **Description**: Create a `middleware.ts` at the project root that intercepts all `/api/*` requests before they reach route handlers
- **Pros**: Centralized check, runs before any route logic, can block abuse at the edge
- **Cons**: No existing middleware in the project; Edge Runtime has limited library access; requires extracting userId from JWT in middleware context; adds latency to every request including non-AI routes; harder to debug
- **Why rejected**: Project has no existing middleware infrastructure; Edge Runtime constraints complicate auth verification; overkill for the current scale

### Alternative 2: Higher-Order Function Wrapper

- **Description**: Create a `withRateLimit(handler, category)` wrapper that wraps each route handler
- **Pros**: Clean separation, single point of modification per route
- **Cons**: Adds abstraction layer; obscures the request flow; harder to test; inconsistent with existing patterns (no other HOF wrappers in the codebase)
- **Why rejected**: Introduces a new pattern not used elsewhere in the codebase; YAGNI for 6 routes

## Consequences

### Positive

- Consistent with existing `checkAiAccess` pattern — developers already understand this flow
- Minimal changes per route (2-3 lines added)
- Easy to test in isolation
- Explicit category per route — no magic or auto-detection

### Negative

- Each route must be modified individually (6 routes)
- Rate limit logic is duplicated in terms of call site (though the service itself is shared)

### Risks

- **Forgetting to add rate limit to new routes**: Mitigation: document the requirement in project rules; lint rule could enforce in the future.
- **Inconsistent placement across routes**: Mitigation: define a clear ordering standard (auth → rate limit → feature access → business logic).

## Implementation Notes

- Call `checkRateLimit(user.uid, 'category')` immediately after `verifyAuth` or `checkAiAccess` returns null
- The function returns `NextResponse` (429) if rate limited, or `null` if allowed
- Route handler pattern becomes: auth → rate limit → feature access → service call
- Rate limit headers are added to the response inside the rate limiter service, not in route handlers
