# ADR-001: In-Memory Sliding Window Rate Limiter

## Status

Accepted

## Date

2026-07-23

## Context

The application has no request rate limiting mechanism. AI chatbot endpoints and other API routes are vulnerable to abuse, DDoS attacks, and token burn from malicious or excessive requests. The project needs a per-user, per-endpoint rate limiter that is efficient, memory-safe, and aligns with existing architectural patterns (singletons, services, factories).

## Decision

Use an in-memory sliding window rate limiter service as a singleton, storing request timestamps per user+endpoint key in a Map. On each hit, expired entries are pruned and the count is compared against configurable per-endpoint limits defined in a constants file. A configurable time window (default 60 seconds) is supported, with the chatbot using a tighter 5-second effective window (12 requests/min).

## Alternatives Considered

### Alternative 1: Upstash Redis Sliding Window

- **Description**: Use `@upstash/ratelimit` with Redis-backed persistent state for rate limiting
- **Pros**: Persistent across instances and cold starts, production-grade, accurate limits on serverless
- **Cons**: Adds a paid dependency, ~30-100ms latency per request, operational overhead
- **Why rejected**: Adds infrastructure cost and complexity not justified at current scale; can be adopted later as an upgrade

### Alternative 2: Hybrid In-Memory + Redis Upgrade Path

- **Description**: Start in-memory with an abstract interface designed for future Redis backend swap
- **Pros**: Fast to ship, zero cost initially, clean upgrade path
- **Cons**: Two implementations to maintain eventually, cold-start limitation persists until upgrade
- **Why rejected**: YAGNI — premature abstraction before Redis is actually needed

## Consequences

### Positive

- Zero new external dependencies
- Low latency (in-process memory access)
- Aligns with existing singleton/service patterns in the codebase
- Configurable per-endpoint limits via constants file

### Negative

- Memory resets on Vercel serverless cold starts
- Counters not shared across concurrent instances — users may slightly exceed limits during cold starts
- Memory usage grows with active users but is bounded by pruning

### Risks

- **Cold-start bypass**: A user could exceed limits during a cold start. Mitigation: acceptable at current scale; upgrade to Redis when scale demands it.
- **Memory growth**: Unbounded Map entries. Mitigation: aggressive pruning of expired entries on every hit, TTL-based cleanup.

## Implementation Notes

- Implement as a singleton service following `ServiceCooldownManager` patterns
- Use `Map<string, number[]>` (key → array of timestamps) for simplicity
- Constants file for per-endpoint limits: `{ maxRequests: number, windowMs: number }`
- Prune expired timestamps on every request before counting
- Return rate limit info in response headers (`X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`)
- Return HTTP 429 with `Retry-After` header when limit exceeded
