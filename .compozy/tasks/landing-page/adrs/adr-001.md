# ADR-001: Separation of Landing Page and Login Page Route Structure

## Status

Accepted

## Date

2026-06-04

## Context

We need to implement a high-fidelity Landing Page for the Levemente application. Previously, the application redirected unauthenticated users visiting the root (`/`) to `/login`. The new Landing Page will serve as the entry portal. We need to decide how to structure the routing between the Landing Page, the Login page, and the Dashboard, particularly for authenticated and unauthenticated users.

## Decision

We will implement **Approach 2: Separate Landing and Minimal Login Page**:
1. The Landing Page will be rendered on the root (`/`) route for unauthenticated users.
2. If an authenticated user visits the root (`/`) route, they will be redirected automatically to `/dashboard`.
3. A dedicated `/landing-page` route will be created to render the Landing Page unconditionally, allowing logged-in users to view it without redirecting.
4. The `/login` route will remain a separate, minimal page dedicated exclusively to authentication (currently displaying Google Sign-In). 
5. The "Login" and "Começar" actions on the Landing Page will redirect unauthenticated users to `/login`.

## Alternatives Considered

### Alternative 1: Unified Landing and Login Page

- **Description**: Render the entire Landing Page on `/login` and `/`, embedding the login card directly at the bottom of the Landing Page.
- **Pros**: Reduced redirection friction.
- **Cons**: Clutters the marketing-focused landing page with complex security / auth logic.
- **Why rejected**: Scale limitation. If we add more authentication methods (e.g., email/password, OTP, other social logins) in the future, the code and visual layout of the landing page will become complex and harder to maintain.

## Consequences

### Positive

- **Flexibility**: We can easily scale and add more login methods (e.g., email/password, Apple login) inside the dedicated `/login` route in the future without modifying the landing page.
- **Clean Architecture**: Separates marketing/informational concern (Landing Page) from user authentication (Login Page).
- **Test Compatibility**: Minimizes changes to existing Cypress tests that directly visit `/login` to sign in.

### Negative

- **Redirection Friction**: Users have to navigate from `/` to `/login` to complete the sign-in process, rather than logging in inline on the home page.

## Implementation Notes

- Modify `app/page.tsx` (Root route) to conditionally render the Landing Page if the user is not logged in, or redirect to `/dashboard` if they are logged in.
- Create `app/landing-page/page.tsx` to unconditionally render the Landing Page.
- Keep `app/login/page.tsx` as a clean, focused login page with the Google Sign-in button.
