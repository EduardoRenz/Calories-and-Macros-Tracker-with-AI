# ADR-002: Modular Component Organization for Landing Page

## Status

Accepted

## Date

2026-06-04

## Context

The Landing Page contains multiple large visual sections (Navbar, Hero, Key Stats, AI Features, Clinical Focus, Visual Demos, Pricing, and Footer). To maintain readability and adhere to the project's overall rules ("Always make Small and Readable Components in pages to be easier to maintain and read"), we need to define where these component files should be stored.

## Decision

We will store all sub-components of the Landing Page in a new modular directory at `components/landing/`. 
The sub-components will be:
- `LandingNavbar.tsx`
- `LandingHero.tsx`
- `LandingKeyStats.tsx`
- `LandingAIFeatures.tsx`
- `LandingClinicalFocus.tsx`
- `LandingVisualDemo.tsx`
- `LandingPricing.tsx`
- `LandingFooter.tsx`

The page routes `app/page.tsx` and `app/landing-page/page.tsx` will import and arrange these sub-components.

## Alternatives Considered

### Alternative 1: Store components inside `app/login/components/`

- **Pros**: Keeps components close to the route they are primarily used in.
- **Cons**: Since the Landing Page will be rendered both in `/` (conditionally) and `/landing-page` (unconditionally), placing them under `app/login/` makes imports less intuitive and scatters shared landing components.

### Alternative 2: Keep all code in a single page file

- **Pros**: Zero initial file creation overhead.
- **Cons**: Results in a file exceeding 1000 lines, violating readability guidelines and making unit testing and maintenance extremely difficult.

## Consequences

### Positive

- **Modularity**: Clean imports, small file sizes, and easy maintenance.
- **Reusability**: Landing sub-components can be easily reused in other pages or sections if needed.

### Negative

- **File Overhead**: Creating multiple small files adds some workspace management overhead.
