# ADR-003: Localized Demo Data Strategy for Landing Page Visual Widgets

## Status

Accepted

## Date

2026-06-04

## Context

The Landing Page mockup shows visual demonstrations (such as a dashboard macro wheel and a meal logging chat interface). These components are meant to be visual representations rather than fully interactive engines. Since the application supports English, Portuguese, and Spanish, the text displayed in these mock previews must be localized.

## Decision

We will define all text content (e.g., meal prompts, bot response text, names of macro categories) under a new `landing.demo` namespace in the translations files:
- `locales/pt.ts`
- `locales/en.ts`
- `locales/es.ts`

Any numerical data (e.g., target percentages, calorie counts, grams of protein) will be passed as component props to avoid duplicate logic. The widgets will render dynamically using standard HTML/CSS structure (such as responsive Tailwind bars and SVG circles) instead of static image mockups, ensuring high accessibility, theme support, and translation rendering.

## Alternatives Considered

### Alternative 1: Hardcoding text in Portuguese or English

- **Pros**: Simplest implementation.
- **Cons**: Completely breaks multi-language support (i18n), violating the overall rules of the project.

### Alternative 2: Storing demo data in a separate static JSON file

- **Pros**: Separates data from presentation.
- **Cons**: Next.js would need to load the locale, locate the JSON, and map it, which adds complexity compared to using the existing `useTranslation` hook architecture.

## Consequences

### Positive

- **Full Translation Coverage**: Compliance with the project's i18n rules.
- **Dynamic Render**: Text expands/collapses properly based on word length in different languages, and values can be easily customized.

### Negative

- **Translation File Growth**: Adds around 20 lines of localized dictionary keys to each translation file.
