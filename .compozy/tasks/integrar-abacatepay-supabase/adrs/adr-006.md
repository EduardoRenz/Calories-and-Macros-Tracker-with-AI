# ADR-006: Optimize The MVP For Correctness And Auditability

## Status

Accepted

## Date

2026-04-25

## Context

The user explicitly prioritized strong correctness over fastest delivery. The chosen product behavior also increases the cost of inconsistent state: cancellation must preserve access until period end, while irregular billing must remove premium promptly. This means duplicate webhook handling, missing event visibility, or weak state transitions would cause directly visible access mistakes.

## Decision

Optimize the MVP for correctness and auditability by including idempotent webhook processing, an explicit inbound event log, reconciliation hooks, and stricter subscription state transitions from the first implementation.

## Alternatives Considered

### Alternative 1: Lightweight MVP with minimal audit trail

- **Description**: Focus on checkout and basic lifecycle writes with limited event history.
- **Pros**: Faster to ship.
- **Cons**: Higher risk of hidden state mismatches and weaker supportability.
- **Why rejected**: It conflicts with the user’s explicit priority and the product’s access rules.

### Alternative 2: Middle path with event log now and reconciliation later

- **Description**: Add idempotency and raw event history now, defer stricter reconciliation behavior.
- **Pros**: Lower immediate scope than a full correctness-first path.
- **Cons**: Leaves operational recovery underdefined in the period when the integration is newest and most fragile.
- **Why rejected**: The user asked to bias toward correctness.

## Consequences

### Positive

- Reduces the chance of access-control mistakes.
- Improves debugging and support investigation.
- Gives future implementation tasks a clearer contract for state changes.

### Negative

- Adds extra implementation work in the first phase.
- Requires more explicit test coverage and monitoring design.

### Risks

- Overengineering is possible if reconciliation surfaces become too elaborate for MVP.
- Stricter transitions may expose gaps in provider event assumptions that need refinement during testing.

## Implementation Notes

- Persist inbound events with processing status.
- Treat state transitions as explicit rules, not loose row overwrites.
- Design reconciliation hooks now even if operator tooling ships later.
