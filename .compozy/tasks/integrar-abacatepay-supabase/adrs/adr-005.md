# ADR-005: Supabase Plans Are The Canonical Product Catalog

## Status

Accepted

## Date

2026-04-25

## Context

The existing app already reads plans from Supabase and renders them on the plans page. The user chose Supabase as the canonical source for recurring products, with provider-specific product identifiers acting as mappings rather than primary product ownership.

AbacatePay requires products to exist before checkout creation and recurring products must include a billing cycle, but that does not require the provider to own the product catalog for the application.

## Decision

Treat Supabase `plans` as the canonical application catalog. Provider-specific plan or product identifiers are stored as external mappings that enable billing operations, but user-facing plan behavior, display data, and plan identity remain owned by Supabase.

## Alternatives Considered

### Alternative 1: AbacatePay product catalog as canonical source

- **Description**: Pull plan data from the provider and mirror only the UI fields locally.
- **Pros**: One less source-of-truth decision for provider metadata.
- **Cons**: Couples product presentation and business identity to the provider and makes migration harder.
- **Why rejected**: It conflicts with the user’s explicit preference and the product’s provider-agnostic goal.

### Alternative 2: Split ownership between marketing metadata and billing metadata

- **Description**: Keep display copy in Supabase but treat billing identity as provider-owned.
- **Pros**: Some local flexibility with limited provider coupling.
- **Cons**: Creates blurred ownership and more frequent synchronization concerns.
- **Why rejected**: It is less crisp than a single canonical catalog with explicit mappings.

## Consequences

### Positive

- Keeps the plan catalog aligned with existing app reads.
- Makes provider replacement a mapping problem instead of a product-definition rewrite.
- Supports localized display content cleanly.

### Negative

- Requires synchronization discipline so provider product IDs remain valid.
- Demands migration or admin scripts when plans change.

### Risks

- Drift between provider product setup and Supabase mappings could block checkout creation.
- Plan changes may require coordinated updates across the app and provider console unless tooling is added.

## Implementation Notes

- Store provider mappings explicitly rather than overloading the plan primary key.
- Keep plan pricing fields normalized enough for the app while preserving provider IDs needed for checkout calls.
