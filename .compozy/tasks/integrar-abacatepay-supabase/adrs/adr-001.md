# ADR-001: Supabase As Source Of Truth For Subscription Access

## Status

Accepted

## Date

2026-04-25

## Context

The product already includes a plans page, a checkout page, subscription context, and Supabase-backed repositories for plans and subscriptions. The payment provider abstraction also already exists, but the active AbacatePay gateway implementation is incomplete. The product goal for the first release is broader than simply collecting payment: users must be able to subscribe through AbacatePay, keep premium access until the end of the paid period after cancellation, lose premium access as soon as billing becomes irregular, and view subscription status plus financial history inside the app.

Because the product may need to change payment providers in the future, the solution should avoid making provider-specific behavior the center of the user-facing subscription model.

## Decision

Use hosted checkout from AbacatePay for payment collection, while treating Supabase as the primary source of truth for customer linkage, subscription access state, cancellation-at-period-end behavior, and user-visible financial history.

The product experience will center on product-owned subscription records and transaction history in Supabase, updated from provider events, rather than reading live provider state directly in the user experience.

## Alternatives Considered

### Alternative 1: Provider-first subscription state with minimal Supabase mirroring

- **Description**: Keep the provider as the effective source of truth and store only the minimum identifiers needed locally.
- **Pros**: Faster to launch and simpler initial data model.
- **Cons**: Weakens provider agnosticism, makes user-facing state more dependent on external APIs, and reduces operational auditability inside the product.
- **Why rejected**: It conflicts with the project direction of prioritizing Supabase and makes a future provider swap more expensive.

### Alternative 2: Full in-app subscription operations and reconciliation in phase one

- **Description**: Launch with hosted checkout plus a rich internal operations layer, extensive manual reconciliation, and advanced exception handling.
- **Pros**: Strong operational control from day one.
- **Cons**: Significantly expands MVP scope and delays validation of the core subscription experience.
- **Why rejected**: It is larger than needed for the initial product outcome and does not follow YAGNI.

## Consequences

### Positive

- Preserves a provider-agnostic subscription domain.
- Keeps user-facing access control and financial history inside the product.
- Supports a clearer future migration path to another provider.
- Aligns with the existing Supabase repository structure already present in the project.

### Negative

- Requires careful event ingestion and state synchronization.
- Introduces product responsibility for keeping subscription state accurate over time.

### Risks

- Delayed or malformed provider events may cause access mismatch unless the product defines clear recovery behavior.
- Product expectations around cancellation, payment failure, and renewal visibility must stay consistent with the provider lifecycle.

## Implementation Notes

- Hosted checkout remains the payment entry point.
- Supabase records should be structured around provider-agnostic customer, subscription, and transaction concepts.
- Provider events should update local product state rather than bypassing it.
