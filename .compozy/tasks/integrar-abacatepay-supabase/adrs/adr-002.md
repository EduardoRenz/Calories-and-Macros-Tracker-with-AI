# ADR-002: Use Supabase Edge Functions For Provider Webhooks

## Status

Accepted

## Date

2026-04-25

## Context

The billing design needs a public HTTPS webhook endpoint that can validate AbacatePay HMAC signatures, process external events idempotently, and persist subscription state in Supabase. The user explicitly chose Supabase as the center of billing state and prefers provider webhooks to terminate inside Supabase rather than the Next.js app.

The current codebase already uses Supabase as the primary data layer for plans and subscriptions. The app also has server-side Supabase admin access, but it does not yet contain a webhook ingestion system.

## Decision

Use Supabase Edge Functions as the public webhook entry point for AbacatePay events. The function will validate the request, record the inbound event, apply idempotent state transitions, and write subscription and transaction changes directly to Supabase tables.

## Alternatives Considered

### Alternative 1: Handle provider webhooks in Next.js API routes

- **Description**: Receive webhook requests in the Next.js application and persist changes from there.
- **Pros**: Reuses the app server and keeps all HTTP surfaces in one place.
- **Cons**: Couples external provider ingestion to the app deployment surface and weakens the clean separation between user actions and provider events.
- **Why rejected**: The user chose Supabase as the billing control plane and this path does not reinforce that boundary.

### Alternative 2: Hybrid webhook ingestion with forwarding between app and Supabase

- **Description**: Accept the webhook in one runtime and forward it to another for persistence.
- **Pros**: Flexibility in where validation and business logic live.
- **Cons**: Adds network hops, more moving parts, and more room for duplicate processing bugs.
- **Why rejected**: It adds complexity without solving an MVP problem.

## Consequences

### Positive

- Keeps provider event handling close to the source of truth.
- Simplifies security ownership for webhook secrets and event persistence.
- Fits the desired Supabase-centered architecture.

### Negative

- Introduces Edge Function deployment and configuration work.
- Requires local and production workflows for public webhook testing.

### Risks

- Misconfigured public access could expose the endpoint incorrectly.
- Signature validation or idempotency bugs could create duplicate state transitions unless tested carefully.

## Implementation Notes

- Configure the webhook function with JWT verification disabled.
- Validate HMAC signatures against the raw request body.
- Persist inbound events before applying business mutations.
