# ADR-003: Redesign Billing Schema Around State Transitions And Event Auditability

## Status

Accepted

## Date

2026-04-25

## Context

The existing `supabase/sqls.sql` billing schema already contains `plans`, `customers`, `subscriptions`, and `transactions`, but it has several structural flaws for a webhook-driven recurring billing system:

- `subscriptions.provider_subscription_id` is mandatory even though the provider subscription identifier may not exist before hosted checkout completes.
- `customers.provider` defaults to `stripe`, which does not match the current provider and is not provider-agnostic.
- `transactions.status` is free text, which weakens consistency.
- There is no durable inbound event table for idempotency, replay visibility, or reconciliation.

The user explicitly asked for a new schema if the current one has flaws.

## Decision

Redesign the billing schema before implementation. Keep the existing conceptual model of plans, customers, subscriptions, and transactions, but reshape it around a provider-agnostic event pipeline with explicit status enums, nullable provider references when lifecycle timing requires it, and separate tables for inbound webhook events and action attempts.

## Alternatives Considered

### Alternative 1: Minimal schema patching

- **Description**: Keep the current schema and only loosen a few constraints.
- **Pros**: Smaller migration and faster initial implementation.
- **Cons**: Leaves auditability and replay safety underpowered and preserves lifecycle assumptions that do not match hosted checkout.
- **Why rejected**: It would move schema debt into core billing flows.

### Alternative 2: Provider-owned schema with shallow product mirrors

- **Description**: Store only the minimum identifiers locally and defer the rest to provider APIs.
- **Pros**: Lower initial schema complexity.
- **Cons**: Weakens provider agnosticism, reduces internal observability, and complicates user-facing history.
- **Why rejected**: It conflicts with the chosen product architecture.

## Consequences

### Positive

- Makes webhook processing idempotent and auditable.
- Allows correct pre-activation and post-activation lifecycle handling.
- Strengthens future provider replacement paths.

### Negative

- Requires more upfront schema work and migration planning.
- Increases the number of tables involved in billing flows.

### Risks

- A rushed redesign could overfit the first provider unless naming and state semantics stay product-oriented.
- Migrating from the current SQL draft will require careful sequencing to avoid confusion during implementation.

## Implementation Notes

- Use separate concepts for inbound provider events, customer mapping, subscription state, and transaction history.
- Keep Supabase `plans` as the product catalog and map providers through external IDs.
- Normalize status values with enums or constrained text domains.
