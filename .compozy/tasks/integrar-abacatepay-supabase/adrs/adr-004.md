# ADR-004: Keep User Actions In Next.js Server Routes

## Status

Accepted

## Date

2026-04-25

## Context

The app already contains Next.js server routes and a payment gateway abstraction. User-initiated actions such as starting checkout and requesting cancellation need authenticated app context, easy access to existing domain code, and tight coordination with current pages such as `/plans` and `/checkout`.

At the same time, provider-originated webhook events are being assigned to Supabase Edge Functions.

## Decision

Keep user-initiated billing writes in Next.js server routes. The app server will create hosted subscription checkouts, request cancel-at-period-end actions against the provider, and persist intent or intermediate state in Supabase using service-role access when necessary.

## Alternatives Considered

### Alternative 1: Move all billing writes into Supabase Edge Functions

- **Description**: Use Supabase Functions for both user actions and provider events.
- **Pros**: Centralizes billing writes in one runtime.
- **Cons**: Adds unnecessary runtime spread for app-native authenticated actions and underuses the existing Next.js server structure.
- **Why rejected**: It does not match the current codebase shape and adds early complexity.

### Alternative 2: Hybrid split where checkout lives in Next.js but cancellation lives in Supabase Functions

- **Description**: Divide app-originated billing writes by action type.
- **Pros**: Some flexibility in operational boundaries.
- **Cons**: More surface area, more duplicated auth concerns, and less predictable ownership.
- **Why rejected**: It is harder to reason about and not needed for MVP.

## Consequences

### Positive

- Reuses existing `app/api` patterns and payment gateway abstractions.
- Keeps user-authenticated flows close to the pages that trigger them.
- Preserves a clear separation between internal actions and external events.

### Negative

- Billing writes will span two runtimes overall: Next.js for user actions and Supabase for webhooks.
- Shared state-transition rules must be documented carefully to avoid divergence.

### Risks

- Without a well-defined contract, Next.js routes and webhook handlers could update the same rows inconsistently.
- Cancel and checkout logic may drift if provider-specific assumptions leak into route handlers.

## Implementation Notes

- Server routes should call provider adapters, not embed provider-specific fetch logic directly in route files.
- The write contract between routes and Supabase tables should be explicit and limited.
